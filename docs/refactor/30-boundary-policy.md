## 1. 정책 원칙 (목표 아키텍처의 이 SDK 구체화)

**코어가 소유한다 — "숫자와 결정":**

1. 검증·정규화: 입력 검증은 **예외가 아니라 정규화로 흡수**한다(§4). 결측 승계·필터·다운샘플(현행 유지).
2. 스케일·틱·좌표: 현행 유지 + **도메인을 출력에 포함**한다(`LineChartLayout`에 축 도메인) —
   렌더러의 tick 역산(AxisScale)이 존재할 이유를 없앤다. "코어가 계산한 값을 렌더러가 역산하면 그건 코어 출력 공백이다"를 규칙으로 삼는다.
3. 상호작용 의미론: 스냅 결과에 정규화 좌표 포함, 스냅 대표 시리즈 선택 규칙, 줌 창 산술(ZoomState),
   도넛 히트테스트(비율 공간), 토글·선택 규칙(현행 유지).
4. 기본값·상수: 플랫폼 중립 수치(비율·임계·간격 정책·컬러맵 앵커·**RGBA 색 값**)는 코어 상수/API로.
   플랫폼 타입 변환(UIColor/Compose Color, dp/pt)만 렌더러.
5. 포맷팅: **코어가 규칙을 소유한다** — 페이스/시간/퍼센트/틱 문자열. ko-KR 고정(05 승인),
   문자열 리소스(존 이름 등 번역 대상)는 앱이 계속 소유하고 값만 주입.
   - **디자인 문서와의 충돌 해소**: `rd-charts-DESIGN.md` §4·비목표는 "단위 포맷 = 앱"으로
     기록돼 있으나, 이는 앱별 포맷 발산(`4'30"` vs `5'30''`)의 직접 원인이 됐다(11 문서 §2).
     본 리팩토링 프롬프트의 목표 아키텍처(포맷팅 코어 회수)를 우선하며, 실행 시
     rd-charts-DESIGN.md 7장에 결정 변경을 기록한다.
6. 도메인 전처리 회수: "원천 샘플 → 차트 입력"(페이스 계산·x값·HR존 dt·최대심박)은 현재 양 앱이
   **서로 다르게** 구현한 최상류 발산 지점(11 문서 §1) — 코어 신규 API로 회수한다(트랙 C).
   앱에는 "DB 읽기 + 원천 레코드 전달 + 뷰 배치"만 남긴다.

**네이티브가 소유한다:**

- 실제 드로잉(CALayer/Compose DrawScope), Path 조립, 캐싱 전략
- 텍스트 측정·폰트, density/pt 환산, 헤어라인 보정, Dynamic Type/fontScale 정책
- 제스처 **인식**(슬롭·타임아웃·인식기 조율 — 단 SDK가 정하는 임계값은 코어 상수), 햅틱 매핑
- 애니메이션 프레임 구동(파라미터 값은 코어 상수)
- 관용 API 표면(UIView/Composable), 생명주기, 접근성 **전달 메커니즘**(문자열 내용은 주입)

## 2. 드로잉 명령 IR — 평가 결과: **전면 채택 기각, "장면 다이제스트" 채택**

요구된 평가 항목별:

| 평가 항목 | 판단 |
|---|---|
| 표현 가능 범위 | 가능하다 — 현행 프리미티브는 선분·폴리라인·폴리곤·호·라운드사각·텍스트·선형 그라데이션·클립뿐. 커스텀 셰이더·블러 없음 |
| 텍스트 2패스 | 필요하다 — 폭 측정 주입 → 배치 → IR. 현재 이 패턴을 요구하는 곳은 라벨 솎기(이미 코어)와 범례(SDK 밖)뿐이라 **회수 이득이 작다** |
| 애니메이션 | 등장 애니는 진행률 0~1을 프리미티브에 곱하는 구조라 매 프레임 IR 재산출이 불필요하지만, 스크럽(60~120Hz) 마커는 IR 재산출 또는 동적 레이어 분리가 필요 — 복잡도 증가 |
| 부분 채택 | 사실상 이미 절반 존재한다 — 양 렌더러가 **동일한 레이어 이름 계약**("grid", "band.N", "series.main.id"…)과 동일 기하 규칙으로 그린다(raw 인벤토리 §7·§12) |
| 관용 API 충돌 | 크다 — iOS CALayer 유지 트리 + CABasicAnimation, AOS 순수 중간 모델 + DrawCache가 각자 플랫폼 최적화. IR 실행기로 바꾸면 이 최적화를 다시 설계해야 한다 |

**기각 근거(핵심)**: 실측된 발산의 원인 분포가 IR의 해결 범위와 어긋난다. 10 문서 소결 기준
상위 발산은 ① 앱 전처리(IR 무관), ② 코어 출력 공백으로 인한 역산 중복(출력 보강으로 해결),
③ 상수 복제(상수 코어화+가드레일로 해결), ④ 포맷팅(코어 회수로 해결)이다. 드로잉 자체의
발산(이징 1건, tnum 1건)은 소수이고 IR 없이도 고칠 수 있다. IR 전환 비용(양 렌더러 재작성 +
성능 재검증)이 남는 이득(드로잉 기하 diff 가능)에 비해 과하다.

**대신 채택 — 크로스플랫폼 동등성 강제 수단 3종**:

1. **코어 골든 테스트**(5단계): JVM+iosSimulatorArm64 동일 골든 — 코어 계산 전량.
2. **장면 다이제스트(SceneDigest)**: 이미 존재하는 레이어 이름 계약을 공식화한다. 각 렌더러의
   테스트 전용 덤프가 "레이어 이름 + 논리 기하(색 RGBA, 폭, 위치를 논리 단위로)"를 07 하네스
   형식으로 직렬화 → 같은 diff 스크립트로 iOS↔AOS 비교(T2 1e-6). 스냅샷 이미지가 못 하는
   크로스플랫폼 비교를 IR 전환 없이 얻는다. 렌더러 덤프(0.7 §4)의 구현 형태가 이것이다.
3. **상수·정책의 코어 단일 원본화**(트랙 B) + CI 금지 패턴(5단계) — 재발 차단.

## 4. 경계 계약 세칙 (신규 규칙)

1. **역산 금지**: 렌더러·앱은 코어가 이미 계산한 값을 역산하지 않는다. 필요한 값이 출력에 없으면
   코어 출력을 보강한다 (B1·B2의 일반화).
2. **require는 프로그래머 오류에만**: 데이터 유래 입력(창 범위, 표본 수)은 코어가 클램프/폴백으로
   정규화하고, 계약 위반(maxTicks<2 등 정적 오용)만 require를 유지한다. ObjC 경계에서 잡히지
   않는 크래시를 데이터가 유발하면 안 된다(20 문서 §6).
3. **수치 리터럴 신설 금지(렌더러)**: 렌더러 신규 코드에 정책성 숫자 리터럴(비율·임계·간격)을
   추가하지 않는다 — 코어 상수를 참조한다. 예외는 플랫폼 보정(헤어라인 등)뿐. CI 검사(5단계).
4. **문자열 생성 금지(렌더러)**: 렌더러는 표시 문자열을 만들지 않는다 — 코어 포매터 결과 또는
   주입 문자열만 배치한다(접근성 포함).
5. **코어 계산은 IEEE 기본 연산 지향**: libm 의존(log10/pow/sin…)이 필요한 경로는 결정론
   대체(정수 거듭제곱 등)를 우선 검토한다 (A1의 일반화). 하네스가 회귀를 감시한다.
